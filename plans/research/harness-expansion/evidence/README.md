## 1. Executive Purpose & Philosophy

This directory is a standard version-controlled repository of empirical qualification trial evidence, where candidate status remains provisional until genuine captured transcripts from real host runs are committed.

Flow rejects marketing theater, vanity compatibility lists, and false advertising ("quảng cáo ảo"). In accordance with **ADR-0001**, Flow is a host-agnostic discipline layer that owns gates and receipts, never the runtime, and requires zero background daemons. A harness cannot be claimed, documented, or promoted as "supported" merely because a configuration file was committed to a repository or static detection logic was added to `flow doctor`.

Compatibility in Flow requires **"Support Thật" (Honest Support)**:
1. **Mechanical Enforcement:** The harness runtime must genuinely execute Flow's mechanical runner (`runner/flow.sh` or `runner/flow.cmd`), inspect integer exit codes, and unconditionally halt when a gate fails ($\text{exit} \neq 0$).
2. **Context Hygiene:** Rule ingestion must respect host token budgets and lifecycle boundaries without silent middle-out truncation or prompt dilution.
3. **Runtime Portability:** Integrations must operate across isolation boundaries (Docker containers, WSL unmapped paths, sandboxes) without path translation crashes (`ENOENT`).
4. **Zero Pass Hallucination:** An agent must never synthesize, hallucinate, or assume a gate pass without an authentic on-disk receipt generated by Flow's mechanical engine.

## 2. Ledger Governance & Verification Rules

Every qualification attempt deposited into this ledger must adhere to three non-negotiable rules:

### Rule 1: No Promotion Without Committed Transcripts and Attributable Evaluation Records
- Static code detection, file installation parity (`flow doctor` returning `true`), or theoretical documentation alignment grants only **PROVISIONAL CANDIDATE** status.
- A candidate harness may only be promoted to **VERIFIED LIVE SUPPORT** when a qualifying engineer or agent runs a complete live trial on a genuine host machine and commits the raw session transcript, tool call payloads, and attributable markdown evaluation record into this directory.
- No installer default, marketing badge, or documentation update claiming compatibility may merge without the corresponding evidence record committed in `plans/research/harness-expansion/evidence/`.

### Rule 2: Simulation and Prompt-Only Testing Are Strictly Invalid
- Synthetic test harnesses that mock tool execution, LLM-generated self-evaluations, replayed dry-run strings, and prompt-only sandbox conversations are categorically rejected as qualification evidence.
- The trial must run against a **live, active host process** (e.g., active Cursor Composer session, real Windsurf Cascade run, genuine Claude Code CLI process, live Codex CLI execution).
- Transcripts must capture the raw tool invocation payload (e.g., `execute_command`, `run_terminal_cmd`, `bash`), raw stdout and stderr streams, exact integer exit codes, and the unedited agent turn that follows.

### Rule 3: Mandatory Forced-Failure Gate-Stop Verification (Gate 3)
- An integration cannot be verified solely by running a happy-path scenario. LLMs have a strong structural bias toward declaring success.
- Every candidate must be subjected to the standardized broken-artifact fixture (`fixtures/candidate-gate3-failure/flow/00-idea.md`), which contains deliberate open checklist items (`- [ ]`) and unfilled `[FILL: ...]` markers.
- When `flow.sh next` exits with return code `1`, the agent must **HALT IMMEDIATELY**, quote the failure diagnostic, and initiate repair. If the agent ever declares the gate passed, hallucinates stage advancement, or bypasses the mechanical check, the harness is immediately stamped **DISQUALIFIED**.

## 3. Authoritative Specification Hierarchy

Per Flow's architectural rule ("One Home Per Fact", codified in `AGENTS.md`), this ledger records test outcomes and raw evidence while deferring protocol specifications to their single authoritative homes:

1. **Protocol Definition:** The Four-Point Live Verification Protocol is defined authoritatively in [`plans/research/harness-expansion/architecture-compatibility-matrix.md#12-the-four-point-live-verification-protocol`](../architecture-compatibility-matrix.md#12-the-four-point-live-verification-protocol):
   - **Gate 1 (Ingestion):** Host reads skill bundle or rule file without truncation, character clipping, or schema errors.
   - **Gate 2 (Invocation):** Host agent actively invokes `runner/flow.sh` or `flow.cmd` via terminal tools during lifecycle actions.
   - **Gate 3 (Gate-Stop):** Host halts and initiates repair on mechanical `exit != 0`; agent NEVER hallucinates a pass.
   - **Gate 4: State Integrity (Persistence & Readback):**
     - *Stage Progression:* Verified stage artifact (`flow/01-research.md` unlocked, fresh `flow status` readback from disk/git).
     - *Card Lifecycle:* Verified card criteria (`cards/C-NNN.md` verified, clean status when qualifying card commands).
     - *Zero Residency:* State cleanly persisted on disk/git with zero resident background daemons.
2. **Process Governance & Anti-Illusion Traps:** The end-to-end qualification lifecycle, scoring tiers, and known platform traps (such as the Zed pseudo-rule trap, WSL path mapping, and container isolation) are governed by [`docs/harness-qualification-process.md`](../../../docs/harness-qualification-process.md).
3. **Constitutional Invariants:** The daemon prohibition, process token non-ownership, and zero tool interposition constraints are anchored in [`docs/adr/0001-discipline-layer-identity.md`](../../../docs/adr/0001-discipline-layer-identity.md).
