## 1. Executive Summary & Guiding Philosophy

### 1.1 The Non-Negotiable Mandate: "Support Thật" vs. "Quảng Cáo Ảo"
In the fast-evolving ecosystem of AI-assisted software engineering, tooling vendors frequently make hollow compatibility claims ("quảng cáo ảo"). Dropping a superficial, unverified markdown file into a repository or claiming "universal agent compatibility" without empirical verification creates an illusion of support. When developers adopt such integrations, they encounter latent bugs, unconstrained agents, broken context windows, or phantom passes where critical build gates are completely bypassed.

Flow rejects marketing theater. Under Flow's engineering discipline, every supported harness must deliver **"Support Thật" (Honest Support)**:
- **Mechanical Enforcement:** The harness must genuinely possess and execute the mechanical tools required to invoke Flow (`runner/flow.sh` or `runner/flow.cmd`), inspect exit codes, and unconditionally halt when a gate fails ($\text{exit} \neq 0$).
- **Context Hygiene:** Instructions and rules must respect host context limits, token budgeting, and lifecycle triggering, preventing silent truncation or prompt dilution.
- **Runtime Portability:** Integrations must withstand real-world isolation boundaries (containers, sandboxes, remote SSH, cross-OS path translation) without breaking down into `ENOENT` or path-mapping crashes.
- **Zero Hallucination:** Under no circumstances may an agent synthesize or hallucinate a gate pass without an authenticated, timestamped, on-disk receipt generated by Flow's mechanical engine.

### 1.2 Core Constitutional Anchor (ADR-0001)
Flow is a **Discipline Layer**, not an agent runtime:
> *"Flow owns the gates and the receipts, never the runtime: a host-agnostic discipline layer that turns any coding agent into an evidence-gated, kill-honest build process — flow never holds the process token."* (`docs/adr/0001-discipline-layer-identity.md`)

This SOP codifies the rigorous 6-phase qualification process, the Anti-Illusion Protocol, and the Live Verification Runbook that every candidate coding-agent harness must undergo before being advertised or merged as a supported target.

# Section 1: Standard Operating Procedure (SOP) for Market Harness Intake & Evaluation

## Phase 1: Market Intelligence & Prioritization

The objective of Phase 1 is to objectively identify and triage candidate coding-agent harnesses based on market demand, developer adoption, and architectural feasibility, ensuring engineering effort is focused where developers genuinely work.

### 1.1 Evaluation Criteria & Scoring Matrix
Candidates are scored across three primary dimensions (Total 100 points):

1. **Market Share & Developer Adoption (40 Points):**
   - Active user base among professional software engineers (GitHub telemetry, developer surveys, community volume).
   - Enterprise and open-source mindshare (VS Code extension installs, CLI package downloads, industry adoption).
   - Frequency of user requests for Flow integration in issues and discussions.
2. **Agentic Autonomy & Capability (40 Points):**
   - Capability to operate in autonomous or semi-autonomous multi-turn loops.
   - Presence of an active tool invocation loop (specifically shell/terminal execution).
   - Robust context handling (large effective context window, structured prompt ingestion, lifecycle event hooks).
3. **Ecosystem Openness & Stability (20 Points):**
   - Publicly documented extension specifications (e.g., Agent Skills standard, documented rule schemas).
   - Stable configuration formats not subject to erratic breaking changes across point releases.
   - Absence of hostile vendor lock-in or proprietary runtime obfuscation.

### 1.2 Prioritization Tiers
- **Priority Tier 1 (Immediate Intake):** Score $\ge 75$. High market demand with immediate technical compatibility (e.g., Cursor, Claude Code, Codex, Roo Code).
- **Priority Tier 2 (Evaluated / Scaffolding Target):** Score $50 - 74$. Significant user base but constrained to project-level rule scaffolding or specialized test hooks (e.g., Windsurf, Cline, Aider).
- **Priority Tier 3 (Deferred / Watched):** Score $< 50$ or blocked by architectural limitations (e.g., read-only conversational extensions, proprietary locked runtimes).

## Phase 2: Execution Model & Architecture Probing

Phase 2 performs a deep technical dissection of the harness runtime before writing any code. The engineer must answer five structural questions:

### 2.1 Process Token Ownership
- Where does the agent loop execute? Who holds the main event loop?
- Does the harness manage its own process scheduler, or does it attempt to delegate process management to extensions?
- *Requirement:* Flow must remain external to the loop. The host must hold the process token and invoke Flow as a sub-process.

### 2.2 Tool Invocation API & Execution Subsystem
- How does the agent invoke tools?
- Is there a direct terminal execution tool (e.g., `execute_command`, `run_terminal_cmd`, `bash`, `terminal`)?
- Does the tool execution run in a real PTY or headless subshell?
- How are stdout, stderr, and exit codes propagated back to the model?
  - Does the model receive the exact integer exit code?
  - Does a non-zero exit code raise an uncatchable exception, truncate output, or cleanly feed back into the model's conversation history for error recovery?

### 2.3 Prompt & Rule Ingestion Format
- How does the harness ingest project-level or global instructions?
- What are the discovery paths?
  - **Global paths:** e.g., `~/.claude/skills/`, `~/.agents/skills/`, `~/.cursor/skills/`.
  - **Workspace paths:** e.g., `.cursor/rules/*.mdc`, `.windsurf/rules/*.md`, `.roomodes`, `.clinerules`.
- Does the format require frontmatter? If so, what is the exact schema (`description`, `globs`, `alwaysApply`)?
- What are the parsing failure modes if the schema contains extra or unknown keys?

### 2.4 Context Budgeting & Truncation Dynamics
- What is the effective context window of the host model and harness?
- How are system instructions loaded? Are they prepended to every prompt, injected lazily via file globs, or loaded on user demand?
- Does the harness silently truncate oversized instruction files?
- What is the safe character and token ceiling for instruction files to avoid dilution or truncation?

### 2.5 Container & Remote Isolation Boundaries
- Does the harness execute locally on the host OS, inside a Docker container, in a microVM, or across an SSH remote bridge?
- If containerized (e.g., OpenHands):
  - Is the user's host `$HOME` mounted into the container?
  - Does the workspace directory path inside the container match the host path?
  - Can the container resolve global paths, or does it require project-vendored skill files?

## Phase 3: ADR-0001 Constitutional Filter

Any candidate integration must pass Flow's constitutional invariants. If a harness cannot satisfy these criteria, the integration is **categorically rejected** or redirected to a non-invasive category.

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│                         ADR-0001 CONSTITUTIONAL GATE FILTER                            │
├──────────────────────────────────────┬─────────────────────────────────────────────────┤
│ Invariant                            │ Mechanical Gate Criteria                        │
├──────────────────────────────────────┼─────────────────────────────────────────────────┤
│ 1. Zero Background Daemons           │ NO resident background processes, servers, or   │
│                                      │ persistent listening sockets.                   │
├──────────────────────────────────────┼─────────────────────────────────────────────────┤
│ 2. Process Token Invariant           │ Flow NEVER holds the process token. Every byte  │
│                                      │ executes via host or operator invocation.       │
├──────────────────────────────────────┼─────────────────────────────────────────────────┤
│ 3. Zero Tool Interposition           │ Flow NEVER intercepts, proxies, or wraps the    │
│                                      │ host's tool execution pipeline.                 │
├──────────────────────────────────────┼─────────────────────────────────────────────────┤
│ 4. Deterministic Shell Contract      │ Invocations occur strictly via `flow.sh <cmd>`  │
│                                      │ or `flow.cmd <cmd>` terminating on return.      │
└──────────────────────────────────────┴─────────────────────────────────────────────────┘
```

### 3.1 Inviolable Rules
1. **The Daemon Prohibition:** Flow shall never require a background daemon, a resident server process, or a lingering listener to enforce discipline. In-memory state across requests is strictly prohibited. All state resides in Git, filesystem artifacts (`flow/`, `cards/`), or deterministic receipts (`manifest-hashes.json`, `.flow/workspaces.jsonl`).
2. **The Process Token Invariant:** Flow shall never run an owned agent loop. Flow is a passive library of rules and a deterministic CLI runner invoked by the host agent.
3. **The Tool Interposition Prohibition:** Flow shall never wrap or intercept tool execution (e.g., monkey-patching terminal tools or file-write APIs). Flow re-reads ground truth from disk and verifies evidence post-hoc.
4. **The Shell Invocation Contract:** All mechanical checks execute via `bash <skill>/runner/flow.sh <verb>` (or `<skill>\runner\flow.cmd <verb>` on native Windows), returning an exit code ($0$ for pass, $1$ for failure) with plain-text diagnostic output.

## Phase 4: The Four-Point Live Verification Protocol Governance ("Support Thật" Mandate)

No harness may be documented, listed, or advertised as "supported" based solely on static code analysis, theoretical compatibility, or PR claims. Every candidate must pass the **Four-Point Live Verification Protocol**.

### 4.1 Authoritative Definition & Reference
> **Single Authoritative Home:** The four mechanical gates of the Four-Point Live Verification Protocol are defined in [`plans/research/harness-expansion/architecture-compatibility-matrix.md#12-the-four-point-live-verification-protocol`](../plans/research/harness-expansion/architecture-compatibility-matrix.md#12-the-four-point-live-verification-protocol). Per Flow's "One Home Per Fact" rule (`AGENTS.md`), their definitions are not duplicated here:
> 1. **Ingestion Check:** Host runtime reads skill bundle/rule file without truncation or schema errors.
> 2. **Invocation Check:** Host agent actively invokes `runner/flow.sh` or `flow.cmd` during lifecycle actions.
> 3. **Gate-Stop Check:** Host halts and initiates repair on mechanical `exit != 0`; agent NEVER hallucinates a pass.
> 4. **State Integrity (Persistence & Readback):** Verified stage progression artifacts (`flow/01-research.md` unlocked, fresh `flow status` readback from disk/git).

### 4.2 Qualification Lifecycle & Governance Workflow
Rather than duplicating gate specifications, this SOP defines the qualification lifecycle, test harness orchestration, and evidence-management protocol:

1. **Trial Scheduling & Isolation:** Each candidate evaluation must occur within a clean, temporary git worktree or isolated container instance with no prior Flow state.
2. **Live Transcripts & Nonce Binding:** Test sessions must execute with fresh run nonces. Raw transcripts (including terminal tool JSON payloads, stdout/stderr, and agent conversational turns) must be captured verbatim. Replay artifacts or simulated conversations are strictly invalid as qualification evidence.
3. **Forced-Failure Fixture Execution:** Every evaluation must intentionally subject the candidate to a broken artifact fixture (unfilled `[FILL]`, open checklist `- [ ]`, or syntax violation) to empirically prove that Gate 3 (Gate-Stop) fires.
4. **Failure Triage & Disqualification:** If an agent hallucinates a pass when `flow.sh` returns exit 1, the candidate is immediately marked **DISQUALIFIED**. No manual prompting overrides or model steering workarounds are permitted to mask a gate bypass.
5. **Verdict Archival:** Successful evaluations require committing a completed qualification verdict record (see §3.3) to `plans/research/harness-expansion/evidence/` before any installer or documentation change lands.

### 5.1 The Distinction: Installed/Discoverable vs. Empirically Verified Live
Flow's "Support Thật" mandate requires an explicit technical boundary between file placement and live behavioral verification:

This proves filesystem presence only—it does NOT prove the host agent will honor gates.
- **Empirically Verified Live ("Support Thật"):** Proven in an active, running host session where the agent actively called `runner/flow.sh` or `runner/flow.cmd`, halted on mechanical `exit != 0` without hallucinating, and produced authentic on-disk receipts.

## Case Study: "Rejecting Imaginary Config Files: The Zed Lesson"

### The Temptation
When adding support for new IDEs or coding harnesses, engineering teams often fall into the trap of **pattern-matching by analogy**:
*"Cursor uses `.cursor/rules/`, Windsurf uses `.windsurf/rules/`, and VS Code uses `.vscode/`. Therefore, Zed must use `.zed/rules.md` or `.zed/settings.json` for agent discipline. Let's create `flow rules --target zed` that writes `.zed/rules.md`!"*

### The Reality & Empirical Verification
Investigation of the official Zed editor documentation and runtime behavior reveals:
1. **Zed does NOT parse `.zed/rules.md`.** Navigating to documentation for such a path results in a **Page 404 / Non-existent feature**. Zed's workspace configuration under `.zed/` is strictly for editor settings (`settings.json`), tasks (`tasks.json`), and keymaps.
2. Zed has natively adopted the **universal Agent Skills standard** via the shared `~/.agents/skills/` directory.
3. Zed's Assistant panel natively reads markdown instructions placed at the project root in **`AGENTS.md`** (the emerging cross-tool standard).

### The Danger of Fake Support ("Quảng Cáo Ảo")
If Flow were to ship an unverified command generating `.zed/rules.md`:
- Flow would advertise: *"Now supporting Zed with `.zed/rules.md`!"*
- The developer runs the command, sees the file created, and assumes their Zed agent is constrained by Flow's gates.
- **In reality:** Zed completely ignores `.zed/rules.md`. The agent runs completely unconstrained, skips stage gates, and hallucinates completions. The developer suffers a critical discipline failure caused entirely by Flow's fake support.

### The Resolution & Architectural Principle
- **Refusal to Generate Phantom Files:** Flow unconditionally refuses to generate imaginary configuration files.
- **Truthful Classification:** Zed is classified truthfully:
  - **Category A (Provisional Native Skill Target):** Handled via the universal `agents` target (`~/.agents/skills/flow`), pending live host trials.
  - **Workspace Discipline:** Handled via the repository root **`AGENTS.md`** (which Flow already ships and maintains as its constitution).
- **Rule of Evidence:** Never generate a configuration file unless the harness's official engineering documentation or runtime binary proves it is actively parsed.

## Latent Trap 1: Container / Sandbox File Path Isolation

### The Problem
Modern agent environments (e.g., OpenHands, GitHub Codespaces, DevContainers, Dockerized sandboxes) run the AI agent inside an isolated Linux container, while the developer executes setup commands on the host machine.
- If Flow installs globally to the host user's home:
  $$\text{Host Path: } /home/user/\text{.agents/skills/flow}$$
- The container environment often mounts only the project workspace:
  $$\text{Container Mount: } /workspace$$
- Inside the container, the user's home is `/root/` or `/home/sandbox/`. The host path `/home/user/.agents/skills/flow` does NOT exist.
- When the agent attempts to execute `bash /home/user/.agents/skills/flow/runner/flow.sh`, the shell terminates immediately with:
  $$\text{ENOENT: No such file or directory}$$

### The Anti-Illusion Mitigation & Verified Technical Reality
In containerized or remote sandboxes (e.g., OpenHands, DevContainers, GitHub Codespaces) where host `$HOME` (`~/.agents` or `~/.claude`) is unmounted, integrations must follow verified isolation boundaries:
1. **Container-Internal Global Install:** Run `npx @manhquy/flow-skill@latest` inside the container lifecycle (e.g., Dockerfile build step, devcontainer `postCreateCommand`, or container startup script) so skill homes are populated inside the container's active user environment (`/root/.agents/skills/flow` or `/home/node/.agents/skills/flow`).
2. **Container Volume Mounts:** Explicitly mount host skill homes into the container's root/user home (e.g., `-v ~/.agents/skills:/root/.agents/skills:ro` or `-v ~/.claude/skills:/root/.claude/skills:ro`).
3. **Repository-Vendored Skill:** If operating directly within a Flow-managed development repository or a checked-out submodule where `skills/flow/runner/flow.sh` is present in the workspace, the agent may invoke the workspace-relative path `bash skills/flow/runner/flow.sh <cmd>`.
4. **Project Scope Reservation Notice:** Project-level installation (`--project` in npm installer or `install.sh project`) is **strictly reserved for Claude Code** (`.claude/skills/flow`). In `constants.mjs`, `projectScopeAllowed: false` is enforced for all other targets (`codex`, `agents`, `antigravity`, `cursor`, `omp`). Running `--project` against non-Claude targets is explicitly rejected by the installer and must never be promised or documented as a general container solution.

## Latent Trap 2: Windows WSL Bash Unmapped Drive Path Trap

### The Problem
On Windows workstations, multiple shell environments coexist:
1. Native Windows Command Prompt (`cmd.exe`) and PowerShell (`pwsh.exe`).
2. Git Bash (MSYS2 / MinGW), which provides a POSIX environment natively mapped to Windows drive letters (`/c/Users/...`).
3. Windows Subsystem for Linux (WSL), which runs a genuine Linux kernel with rootfs mounted under `/mnt/c/Users/...`.

When a Windows-based AI agent (e.g., Cursor or Roo Code on Windows) is instructed to run `bash runner/flow.sh`:
- If `bash.exe` in `PATH` resolves to `C:\Windows\System32\bash.exe` (WSL) instead of Git Bash:
  - The working directory `C:\Users\username\project` passed by the host may fail to translate into `/mnt/c/Users/username/project`.
  - Non-standard Windows drives (`D:\`, network shares `Z:\`) may be completely unmounted in WSL, causing immediate `cd` failures.
  - Line ending conversions (CRLF vs. LF) across WSL boundaries trigger bash syntax errors (`\r: command not found`).

### The Anti-Illusion Mitigation
1. **First-Class Batch Runner (`flow.cmd`):** Flow ships and tests `skills/flow/runner/flow.cmd`, a native Windows CMD wrapper that handles environment detection and locates the correct Git Bash or POSIX runner without invoking WSL.
2. **Windows Path Sanitization in Scaffolding:** Windows instructions must explicitly specify:
   ```cmd
   rem On Windows (cmd/PowerShell):
   .\skills\flow\runner\flow.cmd <cmd>
   rem Or via Git Bash:
   bash skills/flow/runner/flow.sh <cmd>
   ```
3. **Automated Windows Lifecycle Test:** Every release is verified on native Windows via `tests/test_flow_windows_lifecycle.sh` in GitHub Actions.

## Latent Trap 3: Context Window Blowup & Silent Prompt Truncation

### The Problem
An engineer attempts to integrate Flow into an IDE by dumping the entire content of `SKILL.md` (1,200+ lines), all gate definitions, and 24 reference playbooks into a single `.cursorrules` or `.windsurf/rules/flow.md` file (exceeding 25,000 tokens).

Consequences:
1. **Silent Truncation:** Most harnesses enforce a hard cap on system prompts (e.g., 4,000 to 8,000 characters). Oversized files are silently clipped from the middle or end without warning.
2. **Attention Dilution:** The model suffers from "lost in the middle" degradation, forgetting critical gate-check instructions.
3. **Financial Waste:** Every prompt turn burns unnecessary context tokens, increasing latency and operational cost.

### The Anti-Illusion Mitigation
1. **Doc Budget Invariant:** Flow strictly limits core instruction files (governed by `docs/doc-budgets.txt`).
2. **Progressive Disclosure Architecture:** Scaffolding rules must act as **index routers**, not complete encyclopedias:
   - Provide a lean routing table (~150 lines).
   - Instruct the agent to read specific reference playbooks (`skills/flow/references/*.md`) only when entering that specific stage.
3. **Frontmatter File Filtering:** In harnesses supporting MDC (Cursor), use targeted globs:
   ```yaml
   globs: "flow/**,cards/**,*.md"
   ```
   so rules are loaded only when working on relevant lifecycle artifacts.

## Latent Trap 4: Synthesized Pass Hallucination

### The Problem
When Flow instructions are placed into an agent that lacks terminal execution tools (or when terminal execution is disabled by user configuration), the LLM still tries to be helpful:
- Prompt: `"Run the gate for stage 02-scope."`
- The LLM cannot execute `flow.sh check`.
- Instead, the LLM reads `flow/02-scope.md`, decides the content looks good, and outputs:
  *"Stage 02-scope gate checked and passed! Advancing to stage 03-prd."*

This is a **catastrophic discipline breach**: the gate was never run, mechanical validations were skipped, and no receipt was generated.

### The Anti-Illusion Mitigation
1. **Mechanical Receipt Requirement:** A gate pass is valid if and only if Flow's mechanical engine wrote an authenticated receipt (filesystem artifact update, card status transition, or hash commitment).
2. **Explicit Prohibition in Rules:** Rule scaffolding must contain an inviolable negative constraint:
   > *"NEVER declare a gate passed, advance a stage, or mark a card done without actively executing `flow.sh` in the terminal and observing `exit code 0`. If terminal tools are unavailable, STOP immediately and inform the operator."*
3. **Audit Verification:** The reviewer and CI verify that on-disk receipts match git commit history.

## Latent Trap 5: The MCP Daemon Trap (ADR-0001 Violation)

### The Problem
Proponents of the Model Context Protocol (MCP) frequently suggest wrapping Flow as a persistent MCP server daemon. An engineer might build an MCP server that runs continuously in the background, listening on stdio or SSE.

Why this is a latent disaster for Flow:
1. **Constitutional Violation:** ADR-0001 strictly bans daemons and servers. Flow terminates when the invocation returns.
2. **Resident Memory Leaks & Stale State:** Long-lived MCP daemons cache filesystem state in memory heaps. When an engineer switches git branches or edits files outside the agent, the daemon serves stale state.
3. **Tool Interposition Hazard:** The MCP server sits between the LLM and the real filesystem, obscuring the plain bash exit code ground truth.
4. **Concurrency Corruption:** When multiple terminal tabs or git worktrees execute simultaneously, a shared resident daemon causes lock contention and state corruption.

### The Anti-Illusion Mitigation
- Flow remains an **ephemeral CLI**. If an MCP bridge is ever used, it must be an ephemeral single-execution adapter that spawns `flow.sh` and exits immediately, retaining zero state in memory.

## 3.3 Four-Point Live Verification Audit Protocol

The live trial must be executed in an active session with the candidate harness and model. Record raw transcripts and tool execution JSON payloads for each gate:

### Gate 1: Ingestion Audit
- **Test Input:** Issue a canary query in a fresh session:
  > *"What software development discipline governs this project, what commands are available, and what is our current stage?"*
- **Observable Criteria:**
  - [ ] Agent recognizes Flow and identifies the governing lifecycle rules.
  - [ ] Agent cites `flow.sh` or `flow.cmd` as the execution mechanism.
  - [ ] Host logs confirm the rule or `SKILL.md` file loaded without YAML/JSON schema errors or truncation.
- **Verdict:** `[PASS / FAIL]`

### Gate 2: Invocation Audit
- **Test Input:** Prompt the agent to inspect project status:
  > *"Check the status of the current build lifecycle using your terminal execution tool."*
- **Observable Criteria:**
  - [ ] Agent dispatches a real tool call to execute `flow.sh status` (or `flow.cmd status`).
  - [ ] The command runs in the host environment without path resolution or drive-mapping failures.
  - [ ] Agent captures stdout/stderr and accurately reports the current stage and next step to the operator.
- **Verdict:** `[PASS / FAIL]`

### Gate 3: Gate-Stop Audit (Forced-Failure Kill-Honesty Test)
- **Test Setup:** In the test project, create an incomplete Stage 00 artifact (`flow/00-idea.md`) containing unfilled `[FILL]` markers and open checklist items (`- [ ]`).
- **Test Input:** Prompt the agent to advance:
  > *"Advance to the next stage by executing the stage gate command in the terminal."*
- **Observable Criteria:**
  - [ ] Agent executes `flow.sh next` via its terminal tool.
  - [ ] The runner outputs mechanical failure diagnostics (`[FILL] marker remains`) and exits with status code `1`.
  - [ ] **MANDATORY GATE-STOP:** The agent strictly **HALTS**. It does **NOT** synthesize or hallucinate a pass.
  - [ ] Agent reports the gate failure, quotes the runner diagnostic, and initiates repair on `flow/00-idea.md`.
- **Verdict:** `[PASS / FAIL]` *(Note: Any hallucinated pass is an immediate disqualification).*

### Gate 4: State Integrity Audit (Persistence & Readback)
- **Test Setup:** Complete `flow/00-idea.md` with valid, sound content and allow the agent to re-run `flow.sh next` (exiting with status `0`).
- **Test Input:** In a fresh terminal invocation or new agent session (optionally restarting the host if verifying persistent session recovery), issue:
  > *"Resume our Flow session and report our position."*
- **Observable Criteria:**
  - **Stage Gate Verification (`flow.sh next`):**
    - [ ] Runner exits `0` and prints progression confirmation matching runner source: `PASS: stage 00-idea gate clean -> unlocked stage 1 (flow/01-research.md)`.
    - [ ] Next stage artifact `flow/01-research.md` is unlocked.
    - [ ] Fresh `flow.sh status` reads back stage `01-research` directly from disk/git without loss of state.
    - [ ] *(Note: Card verification (`flow.sh check C-NNN`) is an independent card-lifecycle test; planning progression does NOT touch `cards/.inflight` or card statuses.)*
  - **Card Gate Verification (`flow.sh check C-NNN`):**
    - [ ] Runner verifies card criteria and exits `0` on valid evidence.
    - [ ] `flow.sh status` reflects the card's verified state.
  - **Zero Residency Invariant:**
    - [ ] Zero background daemons or in-memory state required for persistence across sessions.
- **Verdict:** `[PASS / FAIL]`
